# CIOS scaffold fixes: auth protection, DTOs, metadata, schema typo, form integration

The fix commit addresses all five issues from the v1 review. The middleware now uses a public-paths allowlist so every route is protected by default. The type system is explicitly relabeled as presentation-layer DTOs with documentation explaining the boundary. Root layout metadata reflects the CIOS product. The `isManadatory` typo is corrected. Login and register pages now have full Supabase auth integration with email/password and OAuth flows, plus a new `/auth/callback` route for PKCE code exchange. Watch for: the auth callback accepts an unvalidated `next` query parameter that could serve as an open redirect (confirmed); registration immediately navigates to `/dashboard` without handling Supabase's email confirmation requirement (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The middleware rewrite inverts the protection model from opt-in to opt-out: a short `publicPaths` array defines what's open, and everything else requires a session. The remaining concern is that `/auth/callback` is public and redirects to whatever `next` parameter is passed without validating that the target is a local path.

The auth forms are now wired to Supabase with error and loading state. The registration flow assumes signup always produces an immediate session, but Supabase's default behavior requires email confirmation first — if confirmation is enabled, the user hits the middleware wall after redirect.

<summary>Issues (2)</summary>

1. **Open redirect in auth callback** — `src/app/auth/callback/route.ts` reads `searchParams.get("next")` and redirects to `${origin}${next}` without validating that `next` starts with `/` and doesn't contain `//` or protocol-relative paths. An attacker can craft a callback URL with `next=//evil.com` to redirect post-login users off-site. Validate that `next` is a relative path starting with `/` and does not contain a double-slash after the leading slash.
2. **Registration assumes immediate session** — `handleRegister` in `register/page.tsx` calls `router.push("/dashboard")` unconditionally on success, but Supabase's default `signUp` behavior requires email confirmation before issuing a session. If email confirmation is enabled, the user will be redirected to `/dashboard`, have no session, and be immediately bounced back to `/login`. Either check whether the returned session is non-null before redirecting, or show a "check your email" confirmation message when no session is present.

## Open redirect via `next` parameter

The OAuth callback route at `src/app/auth/callback/route.ts` extracts a `next` parameter from the URL and uses it as the post-auth redirect destination:

```typescript
const next = searchParams.get("next") ?? "/dashboard";
// ...
return NextResponse.redirect(`${origin}${next}`);
```

If `next` is `//evil.com`, the resulting URL is `https://cios.example.com//evil.com`, which most browsers interpret as a protocol-relative URL navigating to `evil.com`. The standard mitigation is:

```typescript
const next = searchParams.get("next") ?? "/dashboard";
const safePath = next.startsWith("/") && !next.startsWith("//") ? next : "/dashboard";
```

This is a common OAuth phishing vector where an attacker sends a victim a crafted OAuth initiation link that returns them to a spoofed page after legitimate authentication.

## Registration flow without email confirmation handling

The register page's success path:

```typescript
const { error: authError } = await supabase.auth.signUp({ ... });
if (authError) { /* show error */ return; }
router.push("/dashboard");
router.refresh();
```

Supabase's `signUp` returns successfully (no error) even when email confirmation is pending — it just doesn't issue a session token. The `data.session` field will be `null` in confirmation-required mode. The code doesn't check this, so the user gets pushed to `/dashboard`, where the middleware sees no session and redirects to `/login`. The fix is to inspect `data.session`: if null, display a "verification email sent" message instead of navigating away.

All five issues from the prior review are resolved: middleware uses a public-paths allowlist, types are relabeled as DTOs with Prisma-aligned enums, layout metadata is updated, the schema typo is fixed, and both auth forms have full Supabase integration.
