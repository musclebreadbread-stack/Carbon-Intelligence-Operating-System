# 기업용 Carbon Intelligence Operating System 개발 계획

작성일: 2026-08-06  
대상: Carbon Intelligence Operating System(CIOS)  
목표: 현재 구현된 데모·내부 파일럿 수준의 플랫폼을 실제 기업이 사용하는 멀티테넌트 탄소회계·MRV·검증·공시 플랫폼으로 전환

> 본 문서는 현재 코드베이스, 스키마, 테스트, 배포 설정과 주요 업무 흐름을 검토한 결과를 바탕으로 작성한 실행 계획이다. 이번 검토에서는 소스 코드를 변경하지 않았으며, 계획 문서만 추가한다.

## 1. 경영진 요약

현재 플랫폼은 GHG Protocol 기반 배출량 계산, Scope 1·2·3, 데이터 품질, SBTi 목표, 시나리오, 탄소금융, 공시, 디지털 MRV와 검증을 폭넓게 포함하고 있다. 타입체크·테스트·빌드는 통과하므로 기능을 확장할 수 있는 기술 기반은 마련되어 있다.

그러나 지금 상태로 외부 기업의 실제 데이터를 바로 수용해서는 안 된다. 특히 다음 세 가지가 출시 차단 항목이다.

1. 조직 간 데이터 격리와 권한 검증이 모든 조회 경로에 일관되게 적용되지 않았다.
2. 동일 기간의 계산을 재실행할 때 배출량이 중복 합산될 수 있고, 계산 기준의 불변 스냅샷이 부족하다.
3. 검증 수치와 증빙이 실제 파일·측정·승인 흐름과 완전히 연결되어 있지 않다.

권장 전환 방식은 다음과 같다.

- 1단계: 테넌트 보안과 회계 엔진 무결성을 먼저 완성한다.
- 2단계: 실제 증빙·MRV·검증·보고서 artifact를 연결한다.
- 3단계: SSO, 관리자 기능, 비동기 처리, 관찰성, 백업·복구를 추가한다.
- 4단계: Scope 1·2와 제한된 Scope 3을 대상으로 1~2개 기업 파일럿을 진행한다.

PM 1명, 백엔드 2~3명, 프론트엔드 1명, QA·보안 0.5~1명 기준으로 병렬 진행 시 약 16~20주가 현실적인 범위다. 소규모 단독 개발이라면 6~9개월을 예상한다.

테스트와 빌드는 통과했지만 실제 Postgres/Supabase, Storage, pgvector, Queue, 외부 인증, 배포 환경을 사용한 E2E 검증은 아직 완료되지 않았다. 따라서 현재 결과는 “코드 품질 및 데모 fallback의 안정성”을 보여주며, “기업 운영 준비 완료”를 의미하지 않는다.

## 3. 출시 차단 리스크

### P0-1. 조직 간 데이터 격리

관련 영역:

- `src/lib/auth/active-organization.ts`
- `src/lib/actions/auth.ts`
- `src/lib/data/repositories/audit.ts`
- `src/lib/data/repositories/emission-factor-search.ts`
- `prisma/schema.prisma`의 `AuditTrail`, `DataSource`, 계보·설명 관련 모델

현재 활성 조직 전환은 사용자의 실제 멤버십이 아니라 배포 환경의 활성 조직 목록에 선택 ID가 존재하는지 중심으로 검증한다. 또한 일부 감사 이력, 계보, AI 설명, DataSource, 벡터 검색이 조직 조건 없이 조회될 수 있다. RLS 정책도 확인되지 않았다.

필수 조치:

- `OrganizationMembership` 테이블 도입
- 사용자·조직·역할·상태·초대 만료를 멤버십으로 관리
- 모든 Server Action, Repository, API, Page Read에 인증된 tenant context 적용
- `organizationId` 누락 모델 보강 또는 상위 엔터티를 통한 소유권 검증
- 감사 이력·증빙·버전 이력·계보를 조직 범위로 제한
- emission factor 유사도 검색에 조직 필터 적용
- PostgreSQL RLS를 애플리케이션 권한의 방어 계층으로 추가 검토
- 조직 간 접근 테스트를 모든 핵심 route/action/page에 추가

이 항목이 해결되기 전에는 외부 고객의 실제 데이터를 저장하지 않는다.

### P0-2. 배출량 재계산 및 게시 무결성

관련 영역:

- `src/lib/actions/calculation.ts`
- `src/lib/data/repositories/calculation.ts`
- `prisma/schema.prisma`의 `EmissionCalculation`, `EmissionResult`, `EmissionInventory`

동일 조직·연도의 여러 계산 실행 결과를 조회할 때 선택된 실행만 합산한다는 보장이 부족하다. 재실행 시 결과가 중복될 수 있으며, 계산 기준의 불변 스냅샷도 충분하지 않다. Inventory의 조직·연도 유일 제약과 게시 action의 재게시 동작도 일관되지 않는다.

필수 조치:

- 계산 실행을 독립된 `CalculationRun`으로 모델링
- 실행별 입력 hash와 idempotency key 저장
- GWP 버전, Scope 2 기준, 통합 기준, 배출계수 버전, 단위·반올림 정책을 스냅샷으로 저장
- 결과를 `draft`, `review`, `approved`, `published`, `superseded`, `restated` 상태로 관리
- Inventory가 정확히 하나의 승인된 계산 실행을 참조하도록 변경
- 재작성·정정·재게시 시 이전 보고서와 차이를 보존
- 서버가 상태·승인자·게시 시각을 결정하고 클라이언트 입력을 신뢰하지 않도록 변경
- Decimal 또는 명시적인 정밀도·단위·반올림 정책 적용

### P0-3. 검증 수치와 증빙의 실체화

관련 영역:

- `src/lib/actions/verification.ts`
- `src/lib/data/repositories/verification.ts`
- `prisma/schema.prisma`의 `EvidencePackage`, `AuditEvidence`

검증 중요도 계산에 클라이언트가 전달한 총배출량이 사용될 수 있다. 검증 준비도에는 하드코딩된 증빙 완성도·데이터 품질 점수가 포함되어 있다. 증빙 패키지는 실제 object storage 파일과 명시적으로 연결되지 않는다.

필수 조치:

- 검증 대상 총배출량을 게시된 Inventory에서 서버가 직접 조회
- 검증 의견·중요성·진행률을 서버 계산
- S3 또는 Supabase Storage에 원본 증빙 파일 저장
- 파일 유형·크기·악성코드 검사와 보존 정책 적용
- 파일 hash, 버전, 업로더, 승인자, 업로드 시각, 보존기간 저장
- `EvidencePackageItem`으로 패키지와 증빙을 명시적으로 연결
- 서명 URL과 검증기관별 접근권한 적용
- 검증기관 포털, Finding 처리, 최종 성명서 승인·서명 workflow 구현

### P0-4. MRV 모델 연결

현재 `MeterReading`과 MRV `Measurement`가 분리되어 있어 계측값이 모니터링 계획의 측정값으로 연결되지 않을 수 있다. 모니터링 파라미터가 배출원과 명시적으로 연결되지 않고 이름 추정에 의존하는 부분도 있다.

필수 조치:

- 계측기–시설–배출원–모니터링 파라미터–MRV 계획 관계를 명시화
- 수동·CSV·IoT 측정값을 공통 ingestion 모델로 통합
- 계측기 외부 ID, 측정 시각, 출처, 교정 이력 관리
- 중복 방지용 idempotency key 적용
- 측정값 승인·반려·보정 상태 도입
- MRV 계획·파라미터·측정값의 독립적인 조직 소유권 검증

### P0-5. 운영 보안과 배포 기반

현재 rate limit은 프로세스 메모리 기반이며, 계산 API는 `202`를 반환하지만 실제 계산은 요청 안에서 동기 실행된다. health endpoint도 실제 DB 연결성보다 설정 상태를 확인하는 수준이다.

필수 조치:

- Redis 기반 분산 rate limit과 distributed lock
- 계산·AI·대량 import를 Queue/Worker 기반 비동기 Job으로 변경
- Job 상태·진행률·실패 원인·재시도·취소 API 추가
- `livez`와 `readyz` 분리
- readiness에서 DB, migration, Storage, Queue, pgvector 상태 확인
- 401 Unauthorized와 403 Forbidden 응답 분리
- Sentry 또는 동급 오류 추적, OpenTelemetry, 구조화 로그, correlation ID 적용
- 실제 staging 환경에서 Postgres·Supabase·Storage·pgvector E2E 수행
- 백업 복구훈련과 RPO/RTO 검증

## 4. 기능별 보완 계획

### 4.1 활동자료와 데이터 import

- 시설·사업부·배출원·제품·공급자 간 조직 소유권과 계층 일관성 검증
- 활동자료 수정 시 배출량 규칙과 데이터 품질 재검증
- CSV import를 비동기 Job으로 전환
- 원본 파일 보존, 행별 오류, 재처리, 중복 제거 지원
- 5,000행 제한을 제거하고 대량 파일은 chunk 처리
- 행·파일 단위 import idempotency 적용
- 데이터 입력의 승인·반려·잠금 상태 지원

### 4.2 배출계수와 기준 데이터

- 전역 참조 데이터와 고객 전용 데이터를 명확히 분리
- 기준 데이터 버전·출처·유효기간·승인자 관리
- 고객이 전역 기준 데이터를 임의 변경하지 못하도록 권한 제한
- 상용 배출계수와 규제·산업별 라이선스 정책 정리
- pgvector 인덱스와 실제 DB 유사도 검색 통합 테스트 추가

### 4.3 계산과 Inventory

- 실행별 계산 입력·결과 불변화
- 배출계수와 GWP의 effective date 검증
- 조직·연도별 active published run 보장
- 게시 전 내부 검토와 승인 단계 추가
- 승인 후 수정은 정정·재작성 workflow를 통해서만 수행
- 모든 결과에 설명 trace와 data lineage 연결

### 4.4 검증·MRV·증빙

- 검증기관 역할과 제한된 읽기 권한 추가
- Finding 담당자가 해당 조직의 활성 사용자 또는 지정 검증기관인지 확인
- 측정값 교정 및 데이터 품질 승인 기록
- 증빙 파일 hash와 manifest 생성
- 보존기간, legal hold, 삭제 승인 정책 추가
- Digital Signature와 최종 Verification Statement 연결

### 4.5 공시·보고서

현재 보고서 생성은 `ReportGeneration` 메타데이터 기록에 가까우며 실제 PDF/XLSX/JSON/HTML 산출물이 부족하다.

- 보고서 artifact 생성 및 object storage 저장
- 생성 버전, 입력 calculation run, 파일 hash, 다운로드 권한 저장
- `DisclosureResponse.reportId` 필수화
- 보고서와 요구사항의 복합 유일성 추가
- 문항별 데이터 출처·기간·증빙 연결
- CDP, ISSB, ESRS E1, TCFD, GRI, SASB, TNFD 카탈로그의 버전 관리
- 내부 승인·제출·반려·재제출 이력 추가
- 규제기관 제출은 초기 범위에서 자동 제출보다 export와 승인 workflow를 우선 구현

### 4.6 목표·시나리오·로드맵

- 기준연도 배출량과 현재 배출량은 Inventory에서 서버 계산
- 목표 진행률, 감축률, `isOnTrack` 값을 클라이언트가 임의 입력하지 못하도록 변경
- SBTi 경로·기준 버전과 검증 상태 저장
- 시나리오가 실제 계산 run을 baseline으로 참조하도록 변경
- 가정값의 출처·버전·승인 상태 저장
- 비교 시 모든 metric을 저장하고 단일 metric만 보존하지 않도록 변경
- 로드맵 과제에 담당자, 예산, CapEx/OpEx, 일정, 진행 증빙 추가

### 4.7 탄소금융·크레딧

`ETSPosition`, `RECertificate`, `PPA` 등의 고객 조직 귀속과 업무 흐름을 보강한다.

- registry, serial number, vintage, retirement 상태
- 구매·보유·사용·폐기 workflow
- 이중계상 방지와 credit retirement 증빙
- 계약·가격·승인자·문서 연결
- 조직별 포트폴리오와 역할별 조회 제한

### 4.8 관리자·인증·보안

현재 보안 화면은 조회 중심이며 다음 관리 기능이 부족하다.

- 사용자 초대와 초대 만료
- 역할·권한 변경 승인
- API Key 생성·조회·폐기·rotation
- 세션 강제 종료
- 정책과 보존기간 관리
- SSO/SAML/OIDC
- MFA 강제 및 복구 코드 정책
- SCIM 기반 사용자 lifecycle

`EncryptionKey.keyMaterial`의 DB 저장 방식은 외부 KMS 또는 secret manager 중심으로 재설계한다. 애플리케이션 관리 세션을 사용할 경우 session token은 평문 대신 hash를 저장한다.

### 4.9 API와 AI

- OpenAPI 명세와 contract test 작성
- 모든 list API에 cursor pagination 적용
- 계산·import·AI 실행에 Job ID와 상태 조회 제공
- idempotency key와 webhook 지원
- Redis 기반 rate limit, tenant별 quota, 비용 모니터링
- AI Gateway를 통한 모델 allowlist, 비용 한도, 개인정보 redaction, 보존 정책 적용
- AI 도구 실행 context에 서버 인증 조직과 capability를 강제
- AI가 데이터·설정·보고서를 변경할 경우 사용자 승인 요구

### 4.10 화면·국제화·접근성

- 성공 메시지와 페이지 본문의 하드코딩 영어 문구를 한국어 번역 체계로 통합
- 단위·날짜·통화·시간대 설정 지원
- 키보드 탐색, focus 표시, 색상 대비, 오류 안내 개선
- settings 화면에서 조직의 website·registration number가 올바르게 조회·저장되도록 수정
- 읽기 전용으로 남아 있는 GWP·통합 기준 설정에 실제 설정 workflow 추가
- 실제 route와 불일치하는 `revalidatePath` 상수 정리

## 5. 단계별 실행 로드맵

### 단계 0. 기준선 정리와 보안 패치 — 1주

산출물:

- 원격 branch와 현재 branch의 차이 검토 및 통합 기준 확정
- Next.js 및 보안 취약 의존성 패치
- Next.js middleware deprecation에 따른 `proxy` convention 검토
- 테넌트 위협 모델과 데이터 분류표

- 문서의 테스트 수·모델 수 등 stale 정보 정리

완료 기준:

- high 수준 보안 취약점에 대한 패치 또는 승인된 예외
- 배포 기준 commit과 migration 전략 확정
- production과 demo fallback 정책 명확화

### 단계 1. 테넌트·권한·감사 기반 — 2~3주

산출물:

- `OrganizationMembership`과 권한 모델
- 공통 `AuthorizedTenantContext`
- 조직 범위 repository 패턴
- AuditTrail 조직 귀속과 append-only 정책
- 소유권·관계 검증 유틸리티
- cross-tenant access test suite

완료 기준:

- 사용자가 소속되지 않은 조직의 페이지·API·action·파일에 접근할 수 없음
- 모든 핵심 조회에 조직 조건 또는 검증 가능한 상위 소유권이 존재
- 감사 이력 누락 시 mutation이 성공으로 위장하지 않음

### 단계 2. 계산·Inventory 무결성 — 3~4주

산출물:

- `CalculationRun`
- 계산 입력·배출계수·GWP·Scope 2 기준 스냅샷
- idempotency 및 중복 실행 방지
- Inventory 승인·게시·정정 상태
- Decimal·단위·반올림 정책
- 재계산 차이 보고서

완료 기준:

- 동일 입력을 여러 번 실행해도 최종 게시 합계가 중복되지 않음
- 게시된 결과는 승인된 계산 run을 명시적으로 참조
- 정정 시 과거 게시본과 새 게시본의 차이를 추적 가능

### 단계 3. 활동자료·import·MRV — 3~4주

산출물:

- 비동기 import Job
- 원본 파일과 행별 오류 기록
- 중복 제거와 재시작 가능한 chunk 처리
- MeterReading–Measurement–MonitoringPlan 연결
- 계측기 교정·승인 이력
- 데이터 품질 지표의 실데이터 계산

완료 기준:

- import 중단 후 재개 가능
- 동일 원본 파일 재업로드가 중복 데이터를 만들지 않음
- 계측값이 해당 MRV 계획과 배출원에 직접 연결됨

### 단계 4. 검증·증빙·공시 — 3~4주

산출물:

- 실제 Storage 기반 증빙 패키지
- evidence manifest와 hash
- 검증기관 접근권한
- Finding·승인·서명 workflow
- PDF/XLSX/JSON/HTML 보고서 artifact
- framework catalog와 보고서 버전 관리

완료 기준:

- 검증 수치가 서버의 게시 Inventory와 일치
- 검증기관이 권한 있는 증빙만 열람 가능
- 생성된 보고서의 원본 계산 run과 파일 hash 확인 가능

### 단계 5. 기업 운영·통합 — 3~4주

산출물:

- SSO/MFA 우선 지원
- 관리자 기능
- Redis rate limit
- Queue/Worker
- webhook·notification outbox
- live/readiness health check
- Sentry/OpenTelemetry/운영 대시보드
- 백업·복구 자동화 및 runbook

완료 기준:

- 다중 인스턴스에서 rate limit과 Job 상태가 일관됨
- 외부 서비스 장애 시 재시도와 운영자 확인이 가능
- staging 장애 복구 리허설 완료

### 단계 6. 제한적 기업 파일럿 — 2~3주

초기 파일럿 범위:

- Scope 1·2 중심
- 제한된 Scope 3 카테고리
- 1개 공시 프레임워크
- 1개 검증 workflow
- 1~2개 고객 조직

파일럿 중에는 모든 국가별 규제 자동 제출, 실시간 IoT 전체 연동, 자율적인 AI 쓰기 작업을 범위에 넣지 않는다.

## 6. 권장 데이터 모델 변경

다음 모델 변경은 migration 설계와 함께 진행해야 한다.

| 영역 | 권장 변경 |
|---|---|
| 조직 | `OrganizationMembership`, 조직별 역할·상태·초대 정보 |
| 감사 | `AuditTrail.organizationId`, actor 관계, 복합 인덱스, 보존·archive 정책 |
| 계산 | `CalculationRun`, 입력 hash, 기준 버전, 상태, 승인자 |
| Inventory | 계산 run 참조, 게시 버전, 정정·재작성 관계 |
| 증빙 | `EvidencePackageItem`, 파일 hash, storage key, scan·승인 상태 |
| MRV | 계측기·파라미터·계획 관계, 측정 외부 ID, 교정·승인 상태 |
| 공시 | `DisclosureResponse.reportId` 필수, report-requirement 유일성 |
| 기준 데이터 | 전역/조직 전용 구분, 버전·출처·승인 상태 |
| 데이터 소스 | 조직 귀속, credential secret 외부 보관, 연결 상태·동기화 이력 |

`prisma/schema.prisma`를 변경할 때는 프로젝트 규칙에 따라 다음 migration SQL도 반드시 재생성한다.

```powershell
npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script
```

## 9. 최종 권고

CIOS는 기능 범위가 넓고 테스트 기반도 있으므로 폐기보다 “기업 운영 기반을 먼저 보강하는 방식”이 적절하다. 다만 기능 추가를 계속하기 전에 다음 순서를 지켜야 한다.

1. 테넌트 격리와 권한 검증을 완료한다.
2. 계산 결과의 재현성·중복 방지·게시 상태를 완성한다.
3. 증빙·MRV·검증 수치를 실제 데이터와 연결한다.
4. 비동기 처리·운영 관찰성·백업 복구를 구성한다.
5. 제한된 범위로 기업 파일럿을 진행한다.

첫 출시에서는 “모든 ESG 기능”을 약속하기보다, Scope 1·2와 검증 가능한 보고서 생성이라는 명확한 핵심 업무를 안정적으로 제공하는 것이 현실적이다.
